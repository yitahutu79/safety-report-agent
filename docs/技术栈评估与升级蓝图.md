# 技术栈评估与升级蓝图

更新日期：2026-11-03。目标是保留面向公司的报告工作台，同时把检索、技能、工作流、评测和部署升级为可组合、可迁移的系统。组件按阶段引入，避免把多个同类平台叠在一起。

## 当前问题

当前版本已接入 Qdrant Local + FastEmbed 中文向量检索，并与中文关键词召回做 RRF 融合；七个章节使用可移植 `SKILL.md`。v0.9.0 已以 LangGraph StateGraph 编排章节资料规划、受限检索工具、写作、质量审核和一次返修路由。仍未实现独立 reranker、跨项目公司知识库审批流程、LangGraph checkpoint 恢复、Ragas 离线评测集或 RLHF/DPO 训练闭环。

## 评估结论

| 层 | 优先评估的开源组件 | 用途与边界 |
| --- | --- | --- |
| Agent 工作流 | 已接入 LangGraph StateGraph | 当前将资料规划、项目检索、章节写作、确定性质量审核和一次定向返修编排为显式图；保留多模型供应商适配，不授予任意文件系统/网络工具。下一步通过验收样本评估是否增加 checkpoint 和资料不足时的可恢复人工中断。 |
| 技能 | Agent Skills 开放格式 `SKILL.md` | 按报告类型和章节装载专业规则、检索策略、输出结构、禁区和工具。项目里已创建 7 个章节技能并由生成器加载；后续应加技能版本、维护者、适用模板、测试样例和权限。 |
| RAG 引擎 | RAGFlow 作为现成系统做部署/检索 PoC；或应用内使用 Qdrant（二选一） | RAGFlow 提供知识库解析和 HTTP API，适合先评估整套知识层。若它的运行/授权/扩展不合适，则用 Qdrant 做独立检索服务，由本应用控制解析和索引。不要默认同时部署 RAGFlow、Qdrant、Dify 和 FastGPT。 |
| 嵌入与重排 | BGE-M3 + BGE-Reranker-v2-m3 | 面向中文及多语言的开源检索模型；先与当前关键词检索做同一批查询对比。按模型卡逐个核查权重许可、尺寸、速度和公司设备资源。 |
| 混合检索 | 稀疏关键词/BM25 + 向量召回 + RRF 融合 + reranker | 精确保留标准号、物料名、设备位号等字面命中，也召回语义相近内容；随后用 reranker 精排，并按项目、资料角色、文件版本和章节筛选。 |
| 文档解析 | 先对 Docling 做格式和版面评测；扫描件/图纸再独立评估 PaddleOCR | Docling 可把多种 Office/PDF/图像转换成含版面、阅读顺序和表格结构的内容；PaddleOCR 侧重 OCR/文档解析。保留现有 pypdf/docx 解析器作为轻依赖回退，不在未做真实文件对比前替换。 |
| 评测与观测 | 本地可审计 trace + Ragas 指标；再评估 Phoenix 或 Langfuse 自托管 | 留下每次技能版本、检索命中、模型名、输出校验、人工编辑和耗时；建立“相关资料是否找全、答案是否有证据、是否改写、引用是否准确”的离线集。不要把敏感文件原文上传到未审批的云观测服务。 |

## 推荐的目标流程

```text
上传资料
  → 解析为结构化段落/表格并保留页码、表格行、文件哈希
  → 按公司/项目/资料角色隔离知识库，增量建立稀疏与向量索引
  → 章节技能生成多条检索问题，混合召回并重排
  → 整理成“原子事实卡”（事实、阶段、单位、来源、冲突、核验状态）
  → 技能按固定 schema 组织正文/表格，不直接把检索原文当草稿
  → 引用校验、冲突检查、重复/原文相似度检查和章节特定规则检查
  → 失败则限定次数重写并保留错误；成功章节可独立保存
  → 人工审核后生成 Word，并保留 trace、证据快照和可恢复版本
```

RAG 的目标不是“多塞一些原文给模型”，而是提高证据选择质量，并让正文生成拿到经整理的事实卡及来源标识。若模型需要核对某句事实，可以回到对应证据；输出阶段默认不拿整段原文作为写作底稿。每个结论都需可追溯，工程计算和规范适用性由可测的规则工具或专业人员负责。

## 现有组件的取舍

- **RAGFlow**：值得做一个隔离 PoC，优点是现成知识库解析、检索与 API；当前官方快速启动文档声明主要 Docker 目标为 Linux x86-64，虽测试 ARM64 但不维护 ARM 镜像。用户当前开发机是 Apple Silicon，因此本机长期运行不理想；公司 Linux x86-64 服务器更合适。
- **Dify**：可快速搭视觉工作流和知识库，但仓库采用基于 Apache-2.0 且附加条件的 Dify Open Source License。公司集成/再分发前需要合规审查；报告格式、证据快照和工程校验仍要由本应用实现。
- **FastGPT**：具备知识库与可视化工作流，但采用 FastGPT Open Source License，部署前要按其当前条款确认公司使用、分发和服务方式。
- **Qdrant**：适合作为专用检索基础设施，支持向量与稀疏/混合查询；其 Apache-2.0 许可和 API 边界适合本应用独立管理技能及业务状态。小型本地验证可用客户端本地模式；多人生产环境使用服务端，避免多个进程争用本地存储。
- **LangGraph**：已选用并接入章节生成。当前图内使用现有 OpenAI 兼容 provider，因此保持供应商可替换；进度和取消沿用现有工作台。当前还没有持久 checkpoint。启用恢复前需设计持久状态的数据范围、版本兼容、人工补料恢复接口和项目级并发锁。
- **Agent Skills**：采用开放 `SKILL.md` 目录形式作为可移植的专业规则包。Skill 仅给模型说明可做什么和如何做；实际读取项目文件、检索、计算、保存版本仍需受控代码工具。第三方技能需校验来源和权限，不能任由脚本获得任意项目目录访问。
- **RLHF**：不应作为运行时功能。外部托管模型的权重和训练不由本应用控制。近期可以把人工修改、退回原因和最终采纳文本存成经授权的反馈样本，用离线评测改进提示和技能；只有形成足够、脱敏、经专业审核的数据后，才评估公司可控模型的 DPO/RLHF 微调。系统不能自动修改自己的技能、评测标准或安全规则。

## 迁移顺序

1. **先止损**：v0.2.7 的响应解析与失败回退修复已经准备部署；当前失败旧稿需重新生成才会变成新正文，不能把历史回退内容自动当成已改写。
2. **定义评测基线**：从公司批准的历史项目抽取少量去标识化问答、证据命中和章节示例；让工程师标注相关证据、事实准确性、表达质量、引用与遗漏。比较当前检索、BGE-M3、RAGFlow 和 Qdrant，先看结果再定引擎。
3. **PoC RAGFlow vs Qdrant**：用同一份获准的混合资料测表格、标准号、相似语义、PDF 页定位、冲突隔离、增量更新、重删、导出证据定位和 API 稳定性；在 Linux x86-64 公司测试机部署 RAGFlow，在本机/容器测试 Qdrant。选定后只保留一个生产检索栈。
4. **Agent 工作流**：LangGraph 章节 Agent 图已接入；下一步把章节 Skill 与输入/输出 schema 版本化，并用经授权样本评测检索命中、事实引用、可读性、成本和返修率，再设计持久 checkpoint 与补料后恢复。
5. **解析与评测**：对 Docling/PaddleOCR 做实际文件集评测；把每次运行的模型、技能、检索证据、JSON 解析、重写原因和人工编辑记录在本地。合格标准由公司工程人员定义。
6. **公司部署**：把浏览器工作台迁移到 Linux 服务，增加企业账户与项目权限、PostgreSQL 元数据、对象存储、异步任务队列、备份和审计。开源组件许可证、模型权重许可、网络出站和数据留存需分别审查。
